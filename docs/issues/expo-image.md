# Issues found in Expo Image

FastImage's maintainers found these while comparing FastImage with Expo Image; FastImage fixes or works around each one in its own code, as described below. They were checked against expo-image 58.0.15 (the expo repository at commit `59dfdddb`, 2026-10-17) on 2026-10-18. Paths are relative to the expo repository. FastImage's benchmark measured expo-image 57.0.5; the code behind the benchmark-backed issues is the same in its npm package and in 58.0.15. Glide's sources weren't read for this file: where an issue depends on Glide's internals, that's said, and it comes from FastImage's notes on Glide 4.16 (expo-image uses Glide 5.0.5). If you maintain Expo Image, feel free to hand this file to your coding agent.

## Android: allowDownscaling={false} can crash with a large image

- **What happens:** with `allowDownscaling={false}`, an image whose decoded bitmap is over the hardware canvas limit (about 100 MB, e.g. 7200 × 7200 px) crashes the app when it's drawn: `RuntimeException: Canvas: trying to draw too large(...) bitmap`.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/ExpoImageViewWrapper.kt`, `createDownsampleStrategy()` returns Glide's `DownsampleStrategy.NONE` when `allowDownscaling` is false. The other branches cap the size with `SafeDownsampleStrategy` (`CustomDownsampleStrategy.kt`), this one doesn't.
- **How to reproduce:** Reproduced and reported upstream with a repro app, [expo/expo#50429](https://github.com/expo/expo/issues/50429): show a 7200 × 7200 JPEG with `allowDownscaling={false}`.
- **How FastImage handles it:** `downsample={false}` decodes at full size up to 16 megapixels (4096 × 4096) and above that at the largest size under it, which Android can still draw ([#1302](https://github.com/DylanVann/react-native-fast-image/pull/1302)).

## Android: a contentPosition string that isn't a number or a percentage throws during layout

- **What happens:** `contentPosition={{ top: '10px', left: 0 }}` (or any string field other than a number, a percentage or `'center'`) throws a `NumberFormatException` on Android when the image is laid out, which isn't caught. The types allow it (`ImageContentPositionValue` includes `string`). On iOS the same value is ignored.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/records/ContentPosition.kt`, `calcOffset()` calls `value.removeSuffix("%").toFloat()` on any string that isn't `"center"`. It runs from `ExpoImageView.applyTransformationMatrix()`, which `onLayout()` calls. `resolveContentPosition()` in `packages/expo-image/src/utils.ts` only checks the string shorthand, not the object's fields.
- **How to reproduce:** Found by reading the code, not run. Render an image with `contentPosition={{ top: '10px', left: 0 }}` on Android.
- **How FastImage handles it:** `objectPosition` parses CSS's `<position>` syntax (keywords, `px` and `%` lengths, edge offsets) and React Native's object form; an invalid value is ignored (centered) with a warning in development, on every platform ([#1298](https://github.com/DylanVann/react-native-fast-image/pull/1298)).

## iOS: a load replaced by no source or an ImageRef still shows and sends onLoad

- **What happens:** when `source` changes to `null` (or an empty array), or to an `ImageRef`, while a url is still loading, the url's load isn't cancelled. When it finishes, its image replaces what the view shows (the `ImageRef`'s image, or the placeholder) and `onLoad` fires for it. Separately, changing `source` to `null` doesn't clear an image already showing on iOS unless there's a placeholder; on Android the view is cleared.
- **Where:** `packages/expo-image/ios/ImageView.swift`, `reload(force:)`: the `guard let source = bestSource else { displayPlaceholderIfNecessary(); return }` returns before `cancelPendingOperation()`, so `pendingOperation` keeps running, and `imageLoadCompleted` then calls `didLoad`, which sends `onLoad` and calls `renderSourceImage`. The `ImageRef` branch of the `source` prop (`ImageModule.swift`) sets `sources = nil` and renders the ref, then reaches the same `reload()`. Nothing in this path sets `sdImageView.image` to `nil`.
- **How to reproduce:** Found by reading the code, not run. Show a slow remote image, and before it finishes set `source` to `null` (or to an `ImageRef` from `useImage`); the remote image appears when its download finishes, with an `onLoad`.
- **How FastImage handles it:** every reload cancels the view's current load, also for a `data:` uri or no source, and anything a replaced load still delivers is ignored. A regression case checks a source change to a `data:` uri while a slow image loads ([#1159](https://github.com/DylanVann/react-native-fast-image/pull/1159)).

## Android: views of different sizes, and a view during a prefetch, download an image again

- **What happens:** an image shown at two sizes at the same time is downloaded once per size. In FastImage's benchmark (16 photos at two sizes at once), Expo Image made 32 requests, where 16 were needed, and showed all 32 images at 516 ms (median), against 348 ms for a library downloading each photo once. A view mounted while `Image.prefetch` of the same url is still downloading downloads it again too.
- **Where:** Glide shares a running load only between requests with the same `EngineKey` (model, size and options); a different size or option starts its own job, and the downloaded file is in Glide's disk cache only after the first job finishes (Glide internals). Views load at their own size (`ImageViewWrapperTarget.getSize()`, `ExpoImageViewWrapper.rerenderIfNeeded()`) with a `GlideUrlWrapper` model and a `ContentFitDownsampleStrategy`, and `prefetch` in `packages/expo-image/android/src/main/java/expo/modules/image/ExpoImageModule.kt` loads a plain `GlideUrl` at the original size with `NoopDownsampleStrategy`. Its comment says quality and downsampling were added to match the view's cache key, but the model, size and downsample option still differ, so a view never joins a prefetch's job.
- **How to reproduce:** Reproduced in FastImage's benchmark (expo-image 57.0.5, "Sizes" in [benchmarks.md](../benchmarks.md#android)). For the prefetch: call `Image.prefetch(url)` for a slow url, mount an `Image` of it before the prefetch resolves, and count the requests the server gets (found by reading the code; FastImage reproduced the same race with Glide before [#1231](https://github.com/DylanVann/react-native-fast-image/pull/1231)).
- **How FastImage handles it:** on Android, requests for one url (or `cacheKey`), of any size, from views, preloads or `getCachePath`, share one download, and each decodes its own size from it ([#1271](https://github.com/DylanVann/react-native-fast-image/pull/1271), [#1231](https://github.com/DylanVann/react-native-fast-image/pull/1231)).

## Android: priority 'high' doesn't move an image ahead of downloads already waiting

- **What happens:** an image with `priority="high"` mounted while many others load is requested after them. In FastImage's benchmark (the grid's 60 photos loading, then the last one opened at the screen's width 100 ms later, with `priority="high"`), Expo Image showed the photo at 748 ms (median; 816 ms at the 90th percentile), downloading it a second time (61 requests); in 6 of 20 runs it showed it within 248–416 ms, in the others within 532–832 ms. FastImage showed it at 280 ms with 60 requests.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/enums/Priority.kt` maps `high` to Glide's `Priority.IMMEDIATE`. In Glide (internals), priority only orders jobs waiting for one of Glide's few source threads; Glide's OkHttp fetcher hands each request to OkHttp (`call.enqueue`) as soon as its job starts, so requests go out in OkHttp's order (first come, first served, 5 per host). A request that joins a load in progress keeps that load's priority. The view's request is also a new download (previous issue).
- **How to reproduce:** Reproduced in FastImage's benchmark (expo-image 57.0.5, "Opening a photo while others load" in [benchmarks.md](../benchmarks.md#android)).
- **How FastImage handles it:** downloads that haven't started wait in FastImage's own queue, ordered by priority (views before preloads), with at most OkHttp's per-host limit waiting on the network per host; a more urgent request for a url whose download is still waiting moves that download up and shares it ([#1271](https://github.com/DylanVann/react-native-fast-image/pull/1271), [#1285](https://github.com/DylanVann/react-native-fast-image/pull/1285)).

## iOS: large images are decoded at full size and then resized on the main thread

- **What happens:** by default (`allowDownscaling`), an image is decoded at full size and then redrawn smaller for the view, on the main thread. In FastImage's benchmark (20 photos of 4000 × 3000 px in small views, iPhone 15 Pro Max), Expo Image took 560 ms (median) to show them, against 328 ms for FastImage, the app used 414 MB once they showed (FastImage 52 MB), and the phone drew no new frame for about 350 ms before they appeared. With `cachePolicy` `'memory'` or `'memory-disk'`, the full-size image is what SDWebImage keeps in its memory cache. With `enforceEarlyResizing` (or `tintColor`), the image is decoded smaller, but to fit inside the view, so a `cover` image whose aspect ratio differs from the view's is enlarged and looks soft.
- **Where:** `packages/expo-image/ios/ImageView.swift`, `didLoad(_:cacheType:imageUrl:)` calls `processImage(_:idealSize:scale:)`, which calls `resize(image:toSize:scale:)` (`ios/Utils/ImageUtils.swift`, a `UIGraphicsImageRenderer` drawing) from SDWebImage's completion block, which SDWebImage calls on the main queue; the manager stores the image in its caches before that. `thumbnailPixelSize(for:)` sets `.imageThumbnailPixelSize` (the view's size in pixels, with `.imagePreserveAspectRatio`) only for `tintColor`, `enforceEarlyResizing` or photo library assets; SDWebImage's thumbnail decoding fits the image inside that size.
- **How to reproduce:** Reproduced in FastImage's benchmark (expo-image 57.0.5, "Large" in [benchmarks.md](../benchmarks.md#ios)); the main-thread resize is from reading the code. Show 20 photos of 4000 × 3000 px from a server in 100 pt views, and watch the app's memory and frame rate in Instruments.
- **How FastImage handles it:** `downsample` (on by default) reads the image's header first and decodes it with ImageIO's thumbnail decoding straight at the size its fit needs (the fill size for `cover`, with EXIF orientation applied), off the main thread; the memory cache keeps that decoded size, and the downloaded file stays in the disk cache, so a larger view decodes again without downloading ([#1158](https://github.com/DylanVann/react-native-fast-image/pull/1158)).

## iOS: an image that was downloading when the app went to the background fails

- **What happens:** if the app goes to the background while an image downloads and stays there for more than 15 seconds, the download fails when the app comes back (`NSURLErrorTimedOut`), so the view gets `onError` and stays empty (or on its placeholder) until something reloads it.
- **Where:** `packages/expo-image/ios/ImageView.swift` loads through `SDWebImageManager` with the shared downloader, whose `downloadTimeout` defaults to 15 s and keeps counting while iOS suspends the download. Nothing in `packages/expo-image/ios` observes the app going to the background or becoming active; `loadingOptions` has `.retryFailed`, which only stops SDWebImage from skipping the url on later loads.
- **How to reproduce:** Found by reading the code; FastImage reproduced the same SDWebImage behavior in its own regression case before [#1139](https://github.com/DylanVann/react-native-fast-image/pull/1139). Load an image from a slow server (e.g. one that sends a part per second), send the app to the background for 20 s, and bring it back.
- **How FastImage handles it:** a download that was running when the app went to the background and fails with a network error is loaded again once the app is active, once per load, without a second `onLoadStart`; `onProgress` continues ([#1139](https://github.com/DylanVann/react-native-fast-image/pull/1139)).

## Android: image requests don't send the app's cookies

- **What happens:** on Android, image requests send no cookies, and cookies set by image responses aren't kept. An image behind cookie authentication (a session cookie set by a `fetch` login) loads on iOS (`.handleCookies`, the shared `HTTPCookieStorage`) and fails on Android.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/okhttp/ExpoImageOkHttpClientGlideModule.kt` builds its client with `OkHttpClientProvider.createClient()`. React Native's `createClientBuilder()` gives each new client an empty `ReactCookieJarContainer`; React Native connects only its own networking module's container to the cookie store, so this client's stays empty (unless the app set an `OkHttpClientFactory`).
- **How to reproduce:** Found by reading the code. Log in with `fetch` against a server that sets a session cookie, then load an image that needs that cookie.
- **How FastImage handles it:** its image client uses Android's cookie store (the one `fetch` and React Native's `Image` use) through OkHttp's `JavaNetCookieJar`, keeps a cookie jar the app set up itself, and sends requests without cookies if the WebView (which holds the store) isn't available, instead of crashing ([#1138](https://github.com/DylanVann/react-native-fast-image/pull/1138)).

## Android: image downloads have no timeout

- **What happens:** a download that stalls (a connection that never answers, or a response that stops sending data) never fails, so the image never shows and never gets `onError`. Since the response body is read on one of Glide's few source threads (Glide internals), a few stalled downloads also hold up other remote images.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/okhttp/ExpoImageOkHttpClientGlideModule.kt` uses `OkHttpClientProvider.createClient()`, whose builder sets connect, read and write timeouts to 0 (none).
- **How to reproduce:** Found by reading the code. Point an image at a server that accepts the connection and then sends nothing, and wait for `onError`.
- **How FastImage handles it:** its image client gets 15-second connect and read timeouts, as SDWebImage uses on iOS, unless the app's own client already has timeouts ([#1271](https://github.com/DylanVann/react-native-fast-image/pull/1271)).

## iOS: prefetch of a url that failed before fails without a request until the app restarts

- **What happens:** after a prefetch of a url fails in certain ways (data that isn't an image, such as a Wi-Fi login page sent with status 200, an invalid url, or network errors other than the connectivity ones), every later `Image.prefetch` of that url resolves `false` without a request ("Image url is blacklisted") until the app is relaunched, even after the server works again.
- **Where:** `packages/expo-image/ios/ImageModule.swift`, `prefetch` uses `SDWebImagePrefetcher.shared`, whose options are `SDWebImageLowPriority` only (no `SDWebImageRetryFailed`). `SDWebImageManager` (`loadImageWithURL:options:context:progress:completed:` and its failure handling) records such failures in `failedURLs` and fails later loads of them without `SDWebImageRetryFailed`. Views use their own `SDWebImageManager` with `.retryFailed`, so they aren't affected, and a view's success doesn't clear the shared manager's list.
- **How to reproduce:** Found by reading the code; FastImage reproduced the same SDWebImage behavior with its `preload-retry` case before [#1177](https://github.com/DylanVann/react-native-fast-image/pull/1177). Prefetch a url whose first response is HTML with status 200 and later ones the image; the second prefetch fails without a request.
- **How FastImage handles it:** preloads pass `SDWebImageRetryFailed`, as views do, so a url that failed is tried again ([#1177](https://github.com/DylanVann/react-native-fast-image/pull/1177)).

## Android: onProgress goes to the view that started a shared load only

- **What happens:** when two views load the same url at the same size and options at the same time, Glide adds the second to the first's load, and only the first gets `onProgress`. If the first view then changes to another source while the second still uses that download, the first keeps getting the old download's progress, interleaved with its new load's.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/ExpoImageViewWrapper.kt`, `rerenderIfNeeded()` sets the view's `progressListener` on its request's `GlideUrlWrapper`, and `okhttp/GlideUrlWrapperLoader.kt` reports progress to the listener of the model the fetch was built from. `GlideUrlWrapper` is a data class whose equality is its `glideUrl` only, so a joining request's model (with its own listener) isn't the one fetching (Glide's `Engine` adds the joining request as a callback of the running job).
- **How to reproduce:** Found by reading the code. Mount two views of the same size with the same slow url and an `onProgress` each; only one gets events.
- **How FastImage handles it:** progress is looked up by the shared download's key, under a lock, for every view with `onProgress` that's loading it (from `onLoadStart` to its `onLoad` or `onError`), so views joining a load, or waiting for a preload's download, get it, and a view gets no progress from an earlier load ([#1271](https://github.com/DylanVann/react-native-fast-image/pull/1271)).

## Android: prefetch starts every url at once and decodes them into memory views don't use

- **What happens:** `Image.prefetch(urls)` starts a Glide request for every url at once, at the default priority, so a long list fills OkHttp's queue ahead of the images the app shows next, and those wait for the prefetches. Each prefetched image is also decoded at full size into Glide's memory cache, where views don't look (they load at their own size, with other options), also with `cachePolicy: 'disk'`.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/ExpoImageModule.kt`, `prefetch`: `urls.forEach { Glide.with(context).load(GlideUrl(it, headers))...submit() }`, with `diskCacheStrategy(NONE)` only for `'memory'` and no `skipMemoryCache` for `'disk'`.
- **How to reproduce:** Found by reading the code. Prefetch 100 urls from a slow server, then mount an image of another url and note when its request arrives.
- **How FastImage handles it:** `preload` loads 3 sources at a time across calls, at low priority unless the source sets one, and resolves with a result per source ([#1133](https://github.com/DylanVann/react-native-fast-image/pull/1133)). A source with `memoryCache: false` is only downloaded, without decoding ([`source.memoryCache`](../../README.md#sourcememorycache)).

## Every view sends every event to JavaScript

- **What happens:** each image sends `onLoadStart`, `onProgress` (on Android, for every chunk read from the network), `onLoad` and `onDisplay` to JavaScript whether or not the app handles them, so a screen of images sends many events nobody uses.
- **Where:** `packages/expo-image/src/ExpoImage.tsx` always passes its own `onLoadStart`, `onLoad`, `onProgress` and `onError` to the native view. On Android, `events/OkHttpProgressListener.kt` invokes `onProgress` for each callback from React Native's `ProgressResponseBody`, and expo-modules-core emits a view's declared events without checking for a handler (Android: `packages/expo-modules-core/android/src/main/java/expo/modules/kotlin/viewevent/ViewEvent.kt`, `invoke()`; iOS: `packages/expo-modules-core/ios/Fabric/ExpoFabricView.swift`, `installEventDispatchers()` installs a dispatcher for every declared event), so `onDisplay` is sent too.
- **How to reproduce:** Found by reading the code. Log the events reaching JavaScript (e.g. with a breakpoint in the native view's event emitter) for a grid of images with no handlers.
- **How FastImage handles it:** JavaScript tells the native view which events have handlers (a bit per event), and images without handlers send nothing ([#1220](https://github.com/DylanVann/react-native-fast-image/pull/1220), and [#1225](https://github.com/DylanVann/react-native-fast-image/pull/1225) for progress in 9.x).

## Android: the cross-fade between two images shows the background mid-fade

- **What happens:** with a `transition`, when a new image (or the image after a placeholder) fades in over the one showing, what's behind the view shows through during the fade: with two opaque images, 25% of the background at the midpoint, a visible dip on a contrasting background.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/ExpoImageViewWrapper.kt`, `onResourceReady()`: when the previous view has a drawable, it animates `previousView.alpha` from 1 to 0 under `newView.alpha` from 0 to 1, at the same time. Composited, that's `new · t + (old · (1 − t) + background · t) · (1 − t)`, so the background contributes `t · (1 − t)`.
- **How to reproduce:** Found by reading the code. Put an image with `transition={1000}` on a red background, change its `source` between two opaque images, and record the screen.
- **How FastImage handles it:** the Android cross-dissolve draws `from · (1 − t) + image · t`, so nothing behind the view shows through ([#1261](https://github.com/DylanVann/react-native-fast-image/pull/1261)).

## Android: clearing the caches needs an Activity, and clearDiskCache blocks Expo's async functions

- **What happens:** `Image.clearMemoryCache()` and `Image.clearDiskCache()` resolve `false` and clear nothing when there's no current Activity (JavaScript running after Android destroyed the Activity, or a headless task). `clearDiskCache` also runs on Expo's single thread for modules' async functions, so every Expo module's async calls wait while the disk cache is deleted.
- **Where:** `packages/expo-image/android/src/main/java/expo/modules/image/ExpoImageModule.kt`, `clearMemoryCache` and `clearDiskCache` start with `appContext.currentActivity ?: return@AsyncFunction false`, though `Glide.get()` takes any context. `clearDiskCache` has no `runOnQueue`, so it runs on `AppContext.modulesQueue` (the `expo.modules.AsyncFunctionQueue` `HandlerThread` in expo-modules-core).
- **How to reproduce:** Found by reading the code. Call `Image.clearDiskCache()` from a headless JS task; or call it with a few hundred MB cached and time another Expo module's async function called right after.
- **How FastImage handles it:** both work with the application context, without an Activity ([#1267](https://github.com/DylanVann/react-native-fast-image/pull/1267)), and the disk cache is cleared on FastImage's own cache thread, in order with its other cache functions ([#1295](https://github.com/DylanVann/react-native-fast-image/pull/1295)).

## contentFit 'none' and 'scale-down' show different sizes on iOS and Android, and iOS 'scale-down' can crop

- **What happens:** with `contentFit="none"` (and `"scale-down"` for an image smaller than the view), a remote image is shown at its pixel size in points on iOS (a 40 × 40 image is 40 pt, as on the web) and in device pixels on Android (about 15 dp on a 2.625× phone). And on iOS, `scale-down` shows a remote image whose size is between the view's size in points and in pixels (e.g. a 300 × 300 image in a 150 pt view on a 3× screen) at 300 pt, cropped to the view, instead of scaled down to fit. With `allowDownscaling={false}` it acts as `none` for any image larger than the view.
- **Where:** iOS: `packages/expo-image/ios/ContentFit.swift` maps `none` and `scaleDown` to `.center`, which draws the `UIImage` at its size in points (remote images get `scale` 1 from `ImageSource.scale`). `idealSize(contentPixelSize:containerSize:scale:contentFit:)` in `ios/Utils/ImageUtils.swift` decides `scaleDown` by comparing the view's size with the image's size divided by the screen scale (100 pt in the example), and returns that size; `shouldDownscale` then sees no need to resize (300 px is not more than 100 pt × 3), so the 300 pt image is shown with `.center`. Scaling down only happens through `processImage`'s resize. Android: `packages/expo-image/android/src/main/java/expo/modules/image/enums/ContentFit.kt`, `toMatrix()` leaves `None` (and a smaller `ScaleDown`) unscaled, at the drawable's intrinsic size, which for Glide's bitmaps is the bitmap's pixels.
- **How to reproduce:** Found by reading the code (FastImage measured the same Android sizes with Glide in its own regression case before [#1282](https://github.com/DylanVann/react-native-fast-image/pull/1282)). Show a 40 × 40 and a 300 × 300 remote image with `contentFit="scale-down"` in 150 pt views on a 3× iPhone and an Android phone.
- **How FastImage handles it:** `objectFit` follows CSS on both platforms: an image's own size is its pixels as points (dp on Android), `scale-down` is the smaller of `none` and `contain`, and Android lays out `none` and `scale-down` itself from the image's own size ([#1282](https://github.com/DylanVann/react-native-fast-image/pull/1282)).

## contentPosition numbers and numeric strings mean different things on iOS and Android

- **What happens:** a number in `contentPosition` (documented as points) is points on iOS and device pixels on Android, so `{ top: 20, left: 20 }` moves the image about 2.6 times less on a 2.625× Android phone. A string that's a number without `%`, such as `'20'` (allowed by `` `${number}` `` in the types), is 20 points on iOS and 20% on Android. With both `left` and `right` (or `top` and `bottom`), iOS prefers whichever is a number, Android the `left` (`top`) one. Placeholders are always centered.
- **Where:** Android: `packages/expo-image/android/src/main/java/expo/modules/image/records/ContentPosition.kt`, `calcOffset()` passes a `Double` to `calcTranslation()` (`ImageUtils.kt`) as a matrix translation in pixels, and treats every other string as a percentage after removing a `%`; `offsetX()` tries `left` before `right`. `ExpoImageView.applyTransformationMatrix()` uses `ContentPosition.center` for placeholders. iOS: `packages/expo-image/ios/ContentPosition.swift`, `distance(from:)` reads a number or a numeric string as points, and `offsetX` tries both edges' distances before percentages.
- **How to reproduce:** Found by reading the code. Show a `contentFit="none"` image with `contentPosition={{ top: 20, left: 20 }}` on both platforms.
- **How FastImage handles it:** `objectPosition` numbers (and `px` lengths) are points on iOS and dp on Android, percentages follow CSS, both edges of one axis are rejected by the types and centered at runtime with a warning, and `defaultSource` is placed the same way ([#1298](https://github.com/DylanVann/react-native-fast-image/pull/1298)).

## blurRadius depends on the image's resolution and the platform

- **What happens:** the same `blurRadius` blurs a large photo much less than a small image on iOS, and blurs differently on iOS and Android: iOS blurs the full-size decoded image (radius / 2, in the image's pixels for remote images) before it's resized for the view; Android blurs the bitmap decoded for the view, on a copy 4× smaller, so its radius is in units of 4 device pixels, and caps it at 25. On Android, each change of `blurRadius` starts a new load, with `onLoadStart` and `onLoad` again.
- **Where:** `packages/expo-image/ios/ImageModule.swift` (`blurRadius` prop, `radius / 2.0`) and `ios/ImageView.swift` (`createTransformPipeline()`, an `SDImageBlurTransformer` that SDWebImage applies to the decoded image before `processImage` resizes it); `SDImageBlurTransformer` multiplies the radius by the image's `scale`. Android: `ExpoImageViewWrapper.kt`, `createPropOptions()` adds `SoftwareBlurTransformation(min(it, 25), 4)`, and the `blurRadius` setter sets `shouldRerender`.
- **How to reproduce:** Found by reading the code. Show a 4000 × 3000 photo and a 300 × 225 copy of it in the same 100 pt view, both with `blurRadius={10}`, on iOS and Android.
- **How FastImage handles it:** the image is blurred at about the size it's shown at, with React Native's iOS box-blur math on both platforms, so a radius looks the same whatever the file's resolution and platform; changing it blurs the image showing again without load events ([#1193](https://github.com/DylanVann/react-native-fast-image/pull/1193), [#1292](https://github.com/DylanVann/react-native-fast-image/pull/1292)).

## iOS: tinted animated images don't play tinted

- **What happens:** an animated GIF or WebP with `tintColor` doesn't play in the tint color.
- **Where:** `packages/expo-image/ios/ImageView.swift`, `setImage(_:contentFit:isPlaceholder:)` sets `image?.withRenderingMode(.alwaysTemplate)` and the view's `tintColor`. `SDAnimatedImageView` draws an animated image's frames itself (`displayLayer:` sets `layer.contents` to each frame's `CGImage`), which `tintColor` doesn't affect, and `sdImageView.animationTransformer` is only set for resizing (`processImage`).
- **How to reproduce:** Found by reading the code, not run. Show an animated GIF with `tintColor="red"`; what it shows (untinted frames, or a still tinted frame if UIKit's template copy isn't an animated image) depends on the class UIKit gives the template copy.
- **How FastImage handles it:** a still image is shown as a template with the view's `tintColor`, and an animated image's frames are tinted as they're decoded, with SDWebImage's `animationTransformer` and `SDImageTintTransformer` ([#1195](https://github.com/DylanVann/react-native-fast-image/pull/1195)).

## configureCache is iOS only, and throws on Android

- **What happens:** `Image.configureCache()` exists only on iOS: on Android the native module has no such function, so calling it throws a `TypeError` (`ImageModule.configureCache is not a function`). On iOS the limits aren't saved (the app has to call it on every launch, after images may already have loaded), there's no age limit, and a lower `maxDiskSize` is only applied at SDWebImage's next cleanup (when the app goes to the background or terminates).
- **Where:** `packages/expo-image/src/Image.tsx`, `configureCache()` calls `ImageModule.configureCache(config)`; only `packages/expo-image/ios/ImageModule.swift` defines it (`Function("configureCache")`, which sets `SDImageCache.shared.config`), and `ExpoImageModule.kt` doesn't. The Android disk cache is Glide's default (`ExpoImageAppGlideModule.applyOptions`, `InternalCacheDiskCacheFactory(context)`).
- **How to reproduce:** Found by reading the code. Call `Image.configureCache({ maxDiskSize: 100 * 1024 * 1024 })` on Android.
- **How FastImage handles it:** `configureCache` works on both platforms and reports the limits and disk usage; starting limits can be set in native config (or its Expo config plugin) so they apply from the first image, runtime changes are saved for later launches, iOS has `maxDiskAge` and applies a lower limit at once, and Android sets Glide's disk cache size ([#1183](https://github.com/DylanVann/react-native-fast-image/pull/1183)).

## writeToCacheAsync replaces a cached image on iOS but not on Android

- **What happens:** writing an image for a `cacheKey` that's already cached replaces it on iOS and keeps the old one on Android, where the promise resolves as if it had been written. On iOS, a file written for a key whose image is in the memory cache doesn't replace the memory entry, so views keep showing the old image until it's evicted. The file isn't checked to be an image, and only `file://` uris are accepted (pickers on Android often return `content://`).
- **Where:** iOS: `packages/expo-image/ios/ImageModule.swift`, `writeToCacheAsync` calls `SDImageCache.shared.store(nil, imageData:, forKey:, toDisk: true)`, which overwrites the file and only updates the memory cache when given an image. Android: `ExpoImageModule.kt`, `writeToCacheAsync` loads a `GlideUrlWithCustomCacheKey` with `asFile()` and `DiskCacheStrategy.DATA`; Glide looks in its disk cache before fetching (Glide internals), so for a key already there it returns the cached file and never reads the new one (`LocalFileGlideModelLoader`). Both throw `WriteToCacheRemoteSourceException` for anything but a file url.
- **How to reproduce:** Found by reading the code. Write image A for a key, show it, then write image B for the same key and show it again on each platform.
- **How FastImage handles it:** `writeToCache(source, file)` behaves the same on both platforms for an image that's already cached (it isn't replaced, and the docs say to use a new `cacheKey`), checks the file is an image, and takes `content://` uris on Android ([#1179](https://github.com/DylanVann/react-native-fast-image/pull/1179)).
